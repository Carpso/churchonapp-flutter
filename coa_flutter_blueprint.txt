The platform provides role-based dashboards for various church leadership positions and integrates secure payment processing through Lenco API (now Lipila — see update above).

# Security Documentation for Church On App

## Overview
This document outlines the security architecture and measures implemented in the Church On App ecosystem to protect user data, financial transactions, and ensure regulatory compliance.

## Security Architecture

### 1. Multi-Tenant Isolation
- **Tenant ID Enforcement**: All database records include a `tenantId` field for strict data separation
- **Firebase Security Rules**: Comprehensive rules preventing cross-tenant data access
- **Role-Based Access Control**: Different permissions for Bishops, Pastors, Apostles, Prophets, Bookshop owners, Vendors, and Riders

### 2. Payment Security
- **Lenco API Integration**: Secure payment processing with mobile money and card support
- **PCI DSS Compliance**: Card data never stored locally, processed through secure channels
- **Encryption**: API keys encrypted at rest using AES-256 encryption
- **Transaction Logging**: All payment transactions logged with security events

### 3. Authentication & Authorization
- **Authentication**: Secure user authentication with email/password and social providers
- **JWT Token Validation**: Proper token validation on all protected endpoints
- **Session Management**: Secure session handling with appropriate timeouts
- **Role Verification**: Strict role checking on all sensitive operations

### 4. Data Protection
- **Input Validation**: All user inputs validated and sanitized
- **Output Encoding**: Proper encoding to prevent XSS attacks
- **SQL Injection Prevention**: Parameterized queries used throughout
- **Rate Limiting**: Implemented to prevent abuse and DDoS attacks

## Security Measures

### 1. Payment Security Features
- **Mobile Money Priority**: Zambian mobile money integration as primary payment method
- **Card Security**: PCI-compliant card processing with tokenization
- **Transaction Monitoring**: Real-time monitoring for suspicious activities
- **Refund Controls**: Secure refund process with proper authorization

### 2. API Security
- **API Key Encryption**: Sensitive API keys encrypted and stored securely
- **Request Signing**: All API requests properly authenticated
- **Rate Limiting**: Per-user and per-IP rate limiting
- **Input Sanitization**: All API inputs validated and sanitized

### 3. Database Security
- **Field-Level Security**: Sensitive fields properly protected
- **Query Optimization**: Prevented N+1 queries and optimized database access
- **Index Security**: Proper indexing without exposing sensitive data
- **Audit Logging**: All database changes logged for security auditing

## Compliance

### Zambian Regulations
- **RTSA Compliance**: All vehicles meet Road Transport and Safety Agency requirements
- **PSV Licensing**: Proper Public Service Vehicle licensing for all transportation services
- **Insurance Requirements**: Valid insurance for all operational vehicles
- **Driver Certification**: Proper driver certifications and clearances

### Data Protection
- **Privacy by Design**: Data minimization and purpose limitation
- **Consent Management**: Proper consent collection and management
- **Data Retention**: Defined retention policies for different data types
- **Breach Notification**: Procedures for security incident response

## Incident Response

### Security Event Handling
1. **Detection**: Automated monitoring for suspicious activities
2. **Logging**: Comprehensive security event logging
3. **Alerting**: Real-time alerts for security incidents
4. **Response**: Defined incident response procedures
5. **Recovery**: Steps for system recovery and restoration

### Vulnerability Management
- **Regular Updates**: Keeping all dependencies up-to-date
- **Security Scanning**: Automated vulnerability scanning
- **Penetration Testing**: Regular security assessments
- **Bug Bounty**: Encouraging responsible disclosure

## Best Practices

### For Developers
- Always validate user inputs
- Use parameterized queries
- Implement proper error handling
- Follow secure coding practices
- Conduct security reviews

### For Administrators
- Regular security audits
- Access control reviews
- Password policy enforcement
- Security awareness training
- Incident response drills

The Instant Split Blueprint

Since Lipila doesn't natively support automated multi-party marketplace splits in a single collection call, your backend logic will orchestrate this transactionally in two distinct phases: Instant Collection ? Conditional Trigger ? Instant Disbursement.
Scenario A: The Church Offering / Event Ticket

    The Condition: The moment the payment clears.

    The Logic Flow:

        A church member pays K100 for an event ticket or offering via the app.

        Lipila fires a successful collection webhook to your backend.

        Your backend instantly processes the payload:

            K5 (5%) stays in your main platform wallet as your commission.

            Your system immediately calls Lipila�s Disbursements API to push K95 (95%) directly to that specific church's mobile money account.

Scenario B: Carpso Ride (The Transport Feature)

    The Condition: When a ride status updates to COMPLETED.

    The Logic Flow:

        The rider books a trip for K60. The app requests payment up front via Lipila to ensure funds are secured.

        The webhook hits your server confirming the payment is successful. The ride begins. (The money is currently in your main merchant wallet).

        The moment the driver updates the ride status to COMPLETED in the app:

            Your backend calculates the split: K3 (5% commission) stays put.

            Your system instantly triggers Lipila�s Disbursements API to push K57 (95%) directly to the driver�s MTN, Airtel, or Zamtel wallet.

Architecture Requirements for Your Backend

To make sure this works without delays or transaction failures, keep these engineering principles in mind:
1. Database Transaction Isolation (Atomicity)

When a condition is met (like a ride completion), the calculation and the API call must happen inside a safe transaction block. If Lipila�s disbursement fails due to a network glitch, your system needs to mark that specific payout as FAILED_RETRIEVABLE so it can auto-retry, ensuring the driver or church doesn't lose their money.
2. Factoring in Lipila�s Transaction Fees

Lipila charges a small fee per transaction for both collections and disbursements. You�ll need to decide how to handle these network costs so they don't eat into your 5% margin:  

    Option A: Your 5% commission is inclusive of the Lipila fee (meaning your net profit is slightly lower than 5%).

    Option B: Pass the transaction fee onto the user during checkout (e.g., if a ticket is K100, the user pays K103 to cover network costs, keeping your K5 commission intact).i choose option B

3. Asynchronous Webhook Workers

Because you are triggering payouts instantly based on conditions, your webhook handlers shouldn't block the main thread. Use a lightweight queue/background worker pattern to process the disbursement API calls immediately after a condition changes. This keeps the application highly responsive.

This instant-payout structure completely eliminates the administrative burden of managing driver/tenant balances and builds massive trust, because people see their money hitting their mobile wallets the second their work is done.



Choosing Option B (passing network fees to the customer) is the smartest move for a bootstrapped marketplace platform. It ensures your 5% commission remains pure revenue, untouched by fluctuating telecom or aggregator tariffs.

Since you are hosting this on your own Vultr VPS, you have total control over the environment. You can build a lightweight, highly performant, and cost-efficient reactive backend without worrying about serverless timeouts or high execution costs.
The Fee Calculation Formula

To protect your 5% margin, your backend must calculate the total checkout price before hitting Lipila�s collection endpoint. Let's assume Lipila charges a standard percentage fee for collections (C%) and a flat or percentage fee for disbursements (D).

When a user initiates a payment for a base amount (A, e.g., a K100 ride or offering), the formula to ensure the final recipient gets exactly 95% of A and you get exactly 5% of A looks like this:
Total Customer Cost=1-C%A+Disbursement Fee(D)?
Concrete Example (Using hypothetical fees: 2% Collection, K2 Disbursement)

If a user wants to buy a K100 church event ticket:

    Base Amount (A): K100

    Platform Commission (5%): K5 (Your net profit)

    Recipient Share (95%): K95 (What the church must receive)

    Calculated Total Checkout Cost: Your system prompts the user's mobile money wallet for roughly K104.08.

        Lipila takes its collection & disbursement cuts from the K104.08, leaving exactly K5 in your wallet and instantly sending K95 to the church.

Vultr Architecture Overview

Since you are running this on a self-hosted Vultr instance, you want an architecture that handles incoming webhooks instantly without dropped requests or race conditions.
1. The Webhook Receiver (The Gateway)

    Keep this endpoint incredibly lightweight.

    When Lipila hits your Vultr server to tell you a ride condition is met or a payment is successful, the receiver should immediately acknowledge the request with a 200 OK.

    Do not make the next API call to Lipila while holding the connection open. If Lipila's server slows down, your server's connections will pool up and crash.

2. The Background Worker/Queue System

    As soon as the webhook receiver accepts the payload, it pushes a job into a local, lightweight queue running on your Vultr server (like BullMQ with Redis, or an internal memory queue if you are keeping it minimal).

    A background worker monitors this queue. It grabs the job, calculates the 95% split, and hits Lipila�s Disbursements API asynchronously.

3. Database Ledger (The Safety Net)

    Before firing the disbursement API, log the transaction state in your database as PENDING_DISBURSEMENT.

    Once Lipila responds with success, update it to DISBURSED.

    If the Vultr server loses connection to the internet mid-transaction, a simple cron job can look for any PENDING_DISBURSEMENT logs older than 5 minutes and automatically retry them. This guarantees no driver or church is left unpaid.

Recommended Tech Stack for your Vultr VPS

To keep resource consumption low while remaining fully reactive, a great setup on a Vultr Linux instance is:

    Runtime: Node.js (Express or Fastify for high-throughput webhook handling).

    Process Manager: PM2 to keep your application running 24/7, auto-restart on crashes, and utilize all CPU cores.

    Reverse Proxy: Nginx or Caddy handling SSL certificates (via Let's Encrypt) and routing traffic to your Node.js app.
